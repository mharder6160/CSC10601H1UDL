UDL Course Blueprint: CSC1060 Computer Science I (Java)

1) Course context and design intent

  • Course: CSC1060 Computer Science I: Java (introductory programming)
  • Design use: Starter-shell foundation for Brightspace/D2L course build
  • Audience: First-term/early-programming students with varied prior coding experience
  • Delivery: Hybrid in source syllabus; online shell supports in-class and out-of-class learning

2) UDL framework implementation

A. Engagement (why learners engage)

  • Weekly “why this matters” opening tied to practical Java tasks
  • Choice of context in selected coding prompts (finance/game/science/text contexts)
  • Low-stakes checks before high-stakes submissions
  • Progress transparency via weekly checklist and estimated time blocks

B. Representation (how information is presented)

  • Every core concept presented in at least two forms:
  • Plain-language explanation
  • Code example with line-by-line notes
  • Optional trace table/flow view
  • Vocabulary list with student-friendly definitions
  • Common error gallery (compiler/runtime) with interpretations

C. Action & expression (how learners demonstrate learning)

  • Multiple acceptable evidence types where appropriate:
  • Runnable Java code
  • Short design/pseudocode note
  • Debugging reflection or test log
  • Rubrics separate correctness from communication/documentation/testing

3) Accessibility and inclusion

  • Page headings follow logical order (h1 > h2 > h3)
  • Descriptive links (no “click here”)
  • Color is never the only way to communicate meaning
  • Tables used only for data with header rows
  • Code blocks use text labels and readable formatting
  • Video/audio items require captions/transcripts ([INSTRUCTOR CONFIRM] workflow)
  • All downloadable docs reviewed with accessibility checker before posting

4) Predictable navigation pattern

Use one standard module pattern every week:

  1. Overview + outcomes + checklist
  2. Learn (mini-lesson and worked examples)
  3. Practice (guided + independent)
  4. Check understanding (low-stakes knowledge check)
  5. Apply (assignment)
  6. Reflect + preview

5) Learner choice and scaffolding

  • “Core” vs “Challenge” practice tiers
  • Optional enrichment resource section in each module
  • Starter-code expectation statements for assignments
  • Milestones for larger projects (plan -> build -> test -> submit)

6) Feedback strategy

  • Fast formative feedback on low-stakes checks (auto feedback where possible)
  • Assignment feedback anchored to rubric criteria
  • One feedforward note required in each graded coding feedback cycle (“next action”)
  • Optional revision path with capped point recovery policy ([INSTRUCTOR CONFIRM] final percentages)

7) Assessment alignment

Assessment forms align to source outcomes:

  • Outcome areas: syntax, data types/operators, control flow, methods, arrays, object-oriented ideas, file I/O/exceptions, recursion
  • Assessment types:
  • Weekly concept/reading quizzes
  • In-class or lab activities
  • Programming projects (module-based)
  • Midterm/final project components

8) Implementation priorities for starter-shell build

  1. Publish Start Here / Welcome page first
  2. Create one reusable weekly template page and duplicate it
  3. Build first 2–3 modules with complete UDL structure before full-term rollout
  4. Attach existing project documents and update instructions for clarity/accessibility
  5. Run accessibility checklist before student release each week

  • Communication SLA (e.g., response within 24/48h)
  • Office hours and support channels
  • Final grading implementation details in D2L gradebook
